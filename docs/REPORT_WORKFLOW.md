# 持续更新参赛报告：工作流

更新：2026-10-28。用户已确认将报告精简为面向评审的主题正文，完整开发时间线保留在历史附录。

## 文档分工

- `docs/report/PROJECT_REPORT.md` 是当前事实主稿，也是展示版 PDF/PPT 的来源。按作品概述、玩法、模型制作、关键技术、验证与限制、展示计划六部分组织。
- `docs/report/HISTORY_V083.md` 封存截至 v0.83 的完整报告。旧文档的“报告 5.x”在该附录查找；其中“最新”、待办、目录和验收状态只代表当时，不再作为当前结论。封存正文不继续追加或覆盖。
- `PROGRESS.md` 记录每轮开发的日期、改动、验证、剩余问题与提交部署状态。
- `docs/evidence/` 保存来源、生成台账、实机图、失败记录、测试摘要及复现方法。历史材料不因正文精简而删除。

这些文件共同组成可追溯资料；当前实现以主稿为准，不维护事实冲突的另一份展示报告。

## 每轮更新方式

1. 先读主稿、PROGRESS 与 PRD，核对当前实现和 Git 状态。
2. 实施并完成适用检查后，直接修订主稿对应主题及状态表，写明真实验证范围。不再把每次修复追加成新的长篇编号章节。
3. 代表性模型、玩法或技术迭代，在主稿保留“问题与目标—设计依据—关键尝试与取舍—采用方案—效果与验证—剩余限制”。次要修复合并概述，完整细节写入证据与进度。
4. 主稿末尾保留本版修订摘要；连续版本日志写入 PROGRESS。清理缓存、进程端口、Git 提交复核、重复 lint/构建流水等留在开发记录。
5. 当前测试汇总按最近执行日期更新；旧性能样本标明测量环境、场景和日期，不能混称为本轮复测。运行时代码不变时，明确未新增浏览器或动作验收。

## 正文必须保留的制作信息

精简不等于只列功能清单。正文仍需直接呈现关键参考图、实际前后对比、方案调整和失败取舍，而非全部用链接替代。原 5.26 等完整案例可在历史附录查阅。

AI 参考插画、Blender 模型渲染、浏览器实机截图分别标注。图注写清版本或日期、用途，以及机位/光照是否一致；不同机位只能说明效果，不冒充受控对比。静态截图不能证明动作连续性或帧时间。

Lux3D 资产应能追溯到任务、输入、原始产物、Blender 处理和运行时采用版本。失败稿保留为历史，不把较小文件自动称为优化成功。积分实查与估算、用户调用授权与第三方许可分开说明。

## 图片与证据

正文精选每项最有说明力的图，完整批次放在证据目录。优先采用已有清晰实图；没有图片时明确缺失，不补造。

版本控制保留报告引用图、精简验证汇总、资产来源/生成记录和复现脚本。逐帧轨迹、扫描数据、原始截图批次和源码快照默认只留本地；不要因“归档”自动提交全部文件。原有被忽略图片需在发布前核对是否随材料包含。

引用历史附录中的已缺失文件时说明缺口，不生成虚假替代图。主稿不得引用不存在的图片。

## PDF/PPT 输出

展示正文从当前主稿导出，完整过程可单独导出历史附录。根据实际排版调整页数，不提前宣称成品页数。

导出前核对本地链接、图片与字体；导出后逐页查看清晰度、图注、分页、表格和敏感信息。仅本地存在的路径不能作为公开作品地址。没有用户要求时，无需制作或发布 PDF/PPT。

## 状态与范围

状态明确区分计划、占位、实现待验证、已验证、已废弃。不同验证范围分别说明，本机测试不替代人工体验或跨设备验收。

仅支持 PC 浏览器。最新功能、模型、声音与公开交付的限制集中在主稿，不重复列已被后续实现替代的旧待办。报告中不出现用户指定排除的外部工程名称，原始来源事实保留在独立证据台账。
