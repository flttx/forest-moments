# 森林拾光参赛报告维护

使评审正文简洁、当前事实准确、制作过程可追溯。遵循用户 2026-10-28 确认的“主题正文 + 历史附录”结构，不继续按开发轮次扩张正文。

## 入口与文件职责

以下路径相对仓库根目录。先读 `PROGRESS.md`、`docs/PRD.md`、`docs/report/PROJECT_REPORT.md`，核对实际文件和 Git 状态；首次采用或流程变化时读 [REPORT_WORKFLOW.md](../../../docs/REPORT_WORKFLOW.md)。仅要求评估报告时先给审查结论；开发变更或用户授权编辑时同步写入。

- `docs/report/PROJECT_REPORT.md`：当前事实主稿，按作品、玩法、模型制作、关键技术、验证与限制、展示计划组织；也是展示版 PDF/PPT 的来源。
- `docs/report/HISTORY_V083.md`：截至 v0.83 的封存全文，保留旧 5.x 章节。旧“最新”、待办和验收状态只属于当时；不得反向覆盖当前主稿，也不继续向该快照追加新开发记录。
- `PROGRESS.md`：每轮日期、改动、检查结果、剩余问题和提交/部署状态。
- `docs/evidence/`：素材来源、生成与优化记录、原始/失败/采用版本图片、测试摘要及复现方法。

## 如何同步而不堆积

1. 找出实际变化及其证据，区分计划、占位、实现待验证、已验证、已废弃；核对用户确认是否已改变旧待办。无头自动检查、人工体验、跨设备测试分别说明。
2. 在主稿的对应主题原位修订功能、方案和限制。代表性迭代保留“问题—设计依据—关键取舍—采用方案—效果与验证”；小修复合并概述，不每轮新增长篇编号章节。
3. 更新主稿版本、日期、本版修订摘要与最新验证范围，同时在 PROGRESS 追加本轮记录。完整连续版本日志、提交哈希、端口进程、缓存清理及重复构建流水留在开发记录或证据中。
4. 删除当前摘要中已过时的说法；需要保留的旧结论明确标为历史。纯文档整理不改变游戏的实现或验收状态，不把旧截图与性能数字写成本轮复测。

## 保留有价值的过程与图片

- 关键 Lux3D/Blender 制作过程、失败取舍和代表性对比必须直接出现在主稿，不能只剩功能清单与外链。原始任务、参数、逐件数据、哈希和全部试稿放在证据中，正文精选。
- 对新生成资产记录输入/任务、原始产物、优化方式、采用版本及实机接入。积分实查与估算分开，用户调用授权与第三方许可分开；未生成、未核验或未采图时明确缺口。
- 图片区分 AI 参考插画、Blender 渲染、浏览器实机，标注日期/阶段和用途。同机位、同光照才称受控前后对比；静态图不能证明动作连续或帧时间改善。筛掉不能说明正文结论的遮挡图，但不删除历史失败证据。
- 正文和报告附录不出现 `my-blog` 名称、相关路径或图注文字。改用具体技术与既有资源说明，保留来源和授权事实在独立台账中；需要中性图片文件名时保留原图，核对副本内容一致。
- 沿用仅 PC 浏览器范围。正文不添加手机布局、触屏控制或移动端验收待办。

## 精简或重组现有报告

重组前保留完整历史快照，附上日期、版本和“历史状态不作为现状”的说明；历史附录不是另一份持续更新的事实主稿。维护原链接可达性和旧章节指引，检查现有附录，避免每轮制造重复快照。

正文保留作品特色、当前玩法、模型来源与制作、少数代表性技术问题、最新验证和真实限制。重复版本摘要、日常维护、全部测试流水与过细参数移入进度/附录/证据。保留失败过程的可追溯性，不以精简为由抹去重要取舍。

结构变化时同步 `docs/REPORT_WORKFLOW.md`、PRD/PROGRESS 的章节指引及本技能中的过时规则，避免后续再次按旧时间线追加。

## 完成检查与导出

- 按项目 AGENTS.md 完成适用的 lint、test、build，记录真实执行结果和环境；不因只改文档重跑全场景或新增视觉验收结论。必要的浏览器检查沿用项目临时目录与清理约定。
- 检查主稿新增/改动的本地链接、图片存在性与可读取性、图注对应、相对路径、排除名称及当前/历史状态一致性。引用图若被 Git 忽略，显式纳入可归档范围，不顺带跟踪整个截图批次。
- 发现历史缺图时明确标注，不补造；主稿不使用失效图片。导出/发布前还需核对图片随材料包含。
- 未获导出请求时不制作 PDF/PPT。导出时从主稿生成，完整历史按需单独输出附录；核验字体、分页、图注、图片和链接，不预先承诺页数。同步报告不自动授权提交、推送、部署或付费调用。
