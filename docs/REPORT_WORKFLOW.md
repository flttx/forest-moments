# 持续更新参赛报告：工作流

**报告主稿**：docs/report/PROJECT_REPORT.md。建立文档即刻更新，不等到完工后补写；最末版本作为 PDF/PPT 来源。

每轮任务：先读主稿 → 实施并测试 → 依据实际完成度更新功能状态表 → 记录技术决策与 Lux3D/Blender 模型生成证据 → 记录性能与缺陷 → 在修订日志新增一行。若没有新截图，要明确说明尚未采集，而非使用无依据的图片。

## 主稿必须包含的过程记录（2026-10-24 用户要求）

思路、方案调整、效果对比和参考图必须直接记录到 `docs/report/PROJECT_REPORT.md`，不能仅用一句完成摘要加证据目录链接代替。

每轮写明：问题/用户反馈与目标、简要设计思路与决策依据、采用或放弃的方案及原因、参考图与其用途、实际实施前后图及观察结论、验证结果与剩余限制。关键参考图和对比截图用相对路径嵌入主稿，旁边标注版本、图像类型、机位/光照是否一致；不同机位只能作效果说明，不冒充受控对比。保留失败记录，不补造当时未执行的方案或未保存的逐字提示词。

本稿 5.26 为记录示例；后续在对应开发章节继续追加。原文件和完整数据留在 `docs/references/`、`docs/evidence/`，主稿承担完整叙述。导出/发布前核对引用图片已随材料包含，尤其检查 Git 忽略的本地截图。

## 证据约定
版本控制只保留报告引用图、精简验证汇总、资产来源/生成记录和可复现脚本。headless 原始输出、逐帧轨迹、扫描/搜索大数据、单次渲染记录及源码文本快照保留本地并忽略，不因“证据归档”自动提交。文档提到此类文件时标为本地原始记录；克隆仓库后需要重新运行对应脚本获得它们。

将视觉证据置于 docs/evidence/<阶段>/<日期>/，成对命名 before/after、overview/closeup，并附 evidence.md 解释每张图的版本、拍摄机位、目的、测试环境和不确定性。不可使用未经验证的 AI 生成概念图冒充游戏截图。截图或视频要能回溯代码版本。

## 评分所需栏目
创意/受众、技术架构、Lux3D 参与的资产及原始生成过程、可视化建模/骨骼/动画优化过程、交互机制、性能/体验、模型迭代前后对比、问题与解决、成果链接、总结。实际比赛细则调整时修订。

## 输出物
推荐 PDF（无需在线报告账号，便于离线评审），可选公开报告链接。定稿前核查中文字体与排版、图片清晰度、所有链接和敏感信息。没有真实图表不要伪造。可以将主稿转换为 DOCX/PDF；建立此项目时尚未导出。

## 状态标签
计划 / 原型占位 / 已实现待体验 / 已验证 / 已废弃。
已实现必须有代码；已验证必须有检验手段或截图。每个章节都遵守。
